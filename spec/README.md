# Spec: toward a verified `Std.Http` HTTP/1.1 receiver

Build: `lake build` (toolchain `nightly-2026-10-20`; depends on the patched copy in `../fix`).

## What is proven

| File | Result | Trusts |
|---|---|---|
| `Spec/Segmentation.lean` | Model of the receive loop (`parseWith`: re-run the parser on the buffer after each read, `.eof` means wait). `segmentationIndependent_iff`: the outcome is the same for every way of splitting the input into reads **iff** the parser is prefix-consistent. | kernel only |
| `Spec/Strict.lean` | Prefix consistency (`PC`) for parsers over the real `Std.Internal.Parsec` types, and lemmas for `pure`, `bind`, `fail`, `attempt`, `any`, `peek!`, `pbyte`, `if`, `optionalUnlessEof`. `optional_attempt_not_pc`: `optional (attempt p)` is not prefix-consistent — the root cause of #15840. | kernel only |
| `Spec/ChunkLine.lean` | `pc_chunkSizeLine`, `pc_lastChunkBody`, `pc_singleHeader`: the verified chunk-size-line, trailer-section and header-line parsers (defined in `../fix/src/HttpFix/Protocol/H1/ChunkLine.lean`) are prefix-consistent on every input. | kernel only |
| `Spec/RequestLine.lean` | `pc_requestLine`: the verified request-line parser (`../fix/src/HttpFix/Protocol/H1/RequestLine.lean`) is prefix-consistent on every input. | kernel only |
| `Spec/Verified.lean` | `prefixConsistent_of_pc` links `PC` to the receive-loop model; `chunkSizeLine_segmentation_independent`. | kernel only |
| `Spec/Real/Server.lean` | In the patched copy, the server's own `parseRequestLineRawVersion`, `parseSingleHeader`, `parseChunkSize` and `parseLastChunkBody` — every parser the HTTP/1.1 receiver runs on request heads and chunked framing — are built on the verified parsers and are prefix-consistent and segmentation-independent, for every input and configuration. | kernel only |
| `Spec/Chunked.lean` | RFC 9112 §7.1 chunked-body grammar as relations on bytes, with a worked example; `ChunkExtItemL`/`ChunkSizeLineL`: the grammar `Std.Http` accepts (RFC plus whitespace after a value-less extension name), and `ChunkExt.lenient`: every RFC `chunk-ext` is in it. | kernel only |
| `Spec/Sound.lean` | `Sound p P`: what a parser consumed when it succeeds, with rules for the `Std.Internal.Parsec` combinators. | kernel only |
| `Spec/ChunkLineSound.lean` | `chunkSizeLine_sound`: whenever the chunk-size-line parser succeeds, the consumed bytes are a chunk-size line in that grammar and the returned size is the value of its hex digits. The implementation's character classes are checked against the spec's over all 256 bytes. | kernel only |
| `Spec/Framing.lean` | RFC 9112 §6.3 request body length as a relation, `Assigns http10 te cl body`, on the values of a request's Transfer-Encoding and Content-Length field lines: chunked when `chunked` is the final transfer coding (not in HTTP/1.0), the Content-Length value when there is no Transfer-Encoding, zero when there is neither, nothing (the server must reject) otherwise. Includes the Transfer-Encoding grammar (RFC 9112 §7, with parameters and quoted strings, and the RFC 9110 §5.6.1 list syntax with empty elements) and `Content-Length = 1*DIGIT`. | kernel only |
| `Spec/FramingFacts.lean` | A comma-separated list of bare tokens, with optional whitespace around the commas, has exactly one reading under that grammar (`listOf_plainNames`, `chunkedIsFinal_of_plain`). | kernel only |
| `Spec/Real/Framing.lean` | `getSize_assigns`: whenever `Message.Head.getSize` — the function the receiver uses to pick a request's body length, unchanged from upstream — picks a length, RFC 9112 §6.3 assigns that length. So it rejects every request the RFC says to reject (`getSize_rejects`: Transfer-Encoding without `chunked` final, Transfer-Encoding in HTTP/1.0, invalid Content-Length), and when it picks chunked the request has no Content-Length (`getSize_chunked_no_contentLength`). Proven about the shipped `Header.ContentLength.parse` and `Header.TransferEncoding.parse`, through Lean's `String.split`, `trimAscii` and `toNat?`; `./check-shipped.sh` re-checks the same file against the toolchain's own `Std.Http` rather than the patched copy. The theorems are stated over the field values recorded in the request head; that those are exactly the request's field lines is the header parser's part (next steps). `getSize` also rejects some requests the RFC would accept (Transfer-Encoding on several lines, with parameters or empty list elements, or with `chunked` twice; a Content-Length list of one repeated value; both fields together); the theorems do not constrain rejections. | kernel only |
| `../fix/src/HttpFix/Protocol/H1.lean` | The protocol machine's read and write loops — `processRead`, `processWrite`, `pullNextChunk` and their helpers, 18 `partial def`s upstream — are total definitions, so they can be reasoned about and always return. Termination: within a message the reader only moves forward through its phases, the header count stays below `maxHeaders`, and each body step reads at least one byte within `maxBodySize` or moves from a chunk-size line to its data; the writer moves from flushing the head to writing the body to `complete` and empties its buffer when it writes. The start-line length limit is checked on the complete line only (`processReceivingStartLine`; FINDINGS §7: otherwise a long request-target gets 400 or 414 depending on where a read ends). The code is otherwise unchanged; the FRO tests, the split tests, and 150 seeds plus 4,987 mutated payloads (`harness/compare.py`) give the same results as the original server. | kernel only |
| `Spec/RequestLineSound.lean` | `requestLine_sound`: the request-line parser consumes optional empty lines and one `method SP request-target SP HTTP-version CRLF`, with a token method and a target of `VCHAR` bytes (so no CR or LF inside the line), and returns the method the token names, the URI parser's result on the target bytes, and the version the digits denote. | kernel only |
| `Spec/HeaderSound.lean` | `singleHeader_sound`: the header-line parser consumes either the `CRLF` that ends the header section or one `field-line CRLF` (token name, colon, OWS, field content, OWS). | kernel only |
| `Spec/Real/Head.lean` | `recorded_header`: when `Std.Http` records a parsed header line, the stored name is the field name in lowercase and the stored value is the field value without the surrounding whitespace (UTF-8 decoding of the ASCII bytes included). | kernel only |
| `Spec/MultiMap.lean` | `vals_ofList`: the header store (`IndexMultiMap`), built by inserting fields in order, returns for each name exactly the values inserted under it, in order. | kernel only |
| `Spec/BodySound.lean` | The body parsers consume exactly their grammar: `parseChunkSize` a chunk-size line; `parseFixedSizeData` and `parseChunkSizedData` the data bytes they return (and the `CRLF` after complete chunk data); `parseLastChunkBody` a trailer section and the final `CRLF`. | kernel only |
| `Spec/Message.lean` | Request messages as relations on bytes (RFC 9112 §2.1, §3, §5, §6, §7.1): `HeadBytes` (empty lines, request line, field lines, `CRLF`), `ChunkedBody` (chunks, last chunk, trailer section), `BodyOf` (a body delimited as `Framing.Assigns` says), `RequestBytes w h d` (one request with head `h` and decoded body `d`), `Requests w n` (`n` requests in a row). Where RFC 9112 lets a recipient choose, the grammar takes the strict option: lines end in `CRLF` only, field values have no `obs-fold`, and Content-Length is one field line with one value. Two choices follow `Std.Http`, documented where they are made: chunk-size lines use the grammar of `Spec/Chunked.lean`, and the request-target is any non-empty run of `VCHAR`. | kernel only |
| `Spec/MessageExamples.lean` | Two requests that satisfy `RequestBytes`: `GET / HTTP/1.1` with `Host: a` and no body, and `POST / HTTP/1.1` with `Transfer-Encoding: chunked` and a body that decodes to `abc`. | kernel only |
| `Spec/Real/Machine.lean` | `reads_requests`: start from a fresh `Machine .receiving` (as the server does) and apply any sequence of the operations the server performs (`Server/Connection.lean`): feeding bytes split in any way, stepping, pulling body chunks, sending a response and its data, answering `Expect: 100-continue`, closing with an error, ending the input. The bytes the reader has consumed are `reader.messageCount` complete request messages followed by the part of the next one that its state describes, and the head it recorded is that message's: the method its token names, the request-target the URI parser makes of its target bytes, its header fields in order, and its version. `nothing_after_rejection`: once the reader has failed (rejected its input) or closed, it stays failed or closed under every further operation and accepts no more bytes. | kernel only |
| `Spec/Unique.lean` | The message grammar splits a byte stream in only one way. `request_unique`: a request message at the start of a stream is determined by the stream (its bytes, head and decoded body). `requests_unique`: two splittings of a stream into request messages agree (one list of messages is a prefix of the other). `chunked_partial_prefix`: the start of a chunked body decodes to the start of what the whole body decodes to. | kernel only |
| `Spec/Real/NoDesync.lean` | `no_desync`: take the bytes the machine has accepted under any sequence of operations, and any split of them into request messages `ms` followed by other bytes (how a front end that uses the same grammar divides the stream). Unless the reader has failed or closed: the requests it has finished and `ms` agree (one list is a prefix of the other); while it reads a request's body, the head it recorded (method, request-target, header fields, version) is that of the next message of `ms`; when it has finished a request, the bytes it consumed for it are that message. `pulled_bodies`: for every request of `ms`, the data of the body chunks `pullBody` handed out for it, in order, is the start of its decoded body (so each chunk is the next piece of the body), and all of it if one of those chunks was marked final. A handler that responds before reading the whole body gets no more of it (the machine drains the rest). | kernel only |
| `Spec/Shift.lean` | `si_requestLine`, `si_singleHeader`, `si_chunkSizeLine`, `si_lastChunkBody`: the verified parsers are shift-invariant: started on two inputs with the same unread bytes, at any positions of any arrays, they give the same result. `Reader.feed` compacts the buffer, so after the same bytes arrive in different reads they sit at different positions. | kernel only |
| `Spec/Tight.lean` | For the chunk-size line, the one line that `parseWith` also checks against a length limit while it is incomplete: `eofEnd_chunkSizeLine`, running out of input is reported with no bytes left unread; `tight_chunkSizeLine`, a success depends only on the bytes it consumed (because no part of the parser before the final CRLF reads past a CR). Together they make the limit check give the same answer on a line and on any extension of it. | kernel only |
| `Spec/Real/Segment.lean` | `si_processRead`, `si_pullBody`: the read loop and the pull loop depend only on the machine's unread bytes, not on where they sit in the buffer. `ce_processRead`, `ce_pullNextChunk`: nothing they compute depends on the event queue. | kernel only |
| `Spec/Real/Absorb.lean` | `read_split`: before the end of input is signalled and before a response is sent, within the buffer limit, feeding `x` and running the read loop, then feeding `y` and running it again, ends in the same machine as feeding `x ++ y` and running it once. "The same" means: up to where the unread bytes sit and the event queue (the split run has extra `needMoreData` events), after finishing a rejection's failure handling, and, once the reader has rejected the input or closed, up to the buffer and the body-byte count, which it no longer reads. `pull_split`: likewise for body pulls. If feeding `x` and pulling hands out nothing, then feeding `y` and pulling hands out the same as feeding `x ++ y` and pulling once, and the machines agree as above; this assumes the chunk being read fits the body limit, which the machine checks on every chunk-size line. The bug (#15840) is a counterexample to `pull_split` in the shipped server: after `5;` it rejects (`test/BugCase.lean`, `test/BugCaseShipped.lean`). Not covered: after a response has been sent, the reader drains the rest of the body, and a split can change how much of a chunk's data it has counted while it waits for the chunk's CRLF; the outputs do not differ (tested by `test/SplitDiff.lean`). Also not covered: pulls that hand out data (the data is cut into chunks as it arrives; `pulled_bodies` covers its content), and the buffer limit `maxBufferedInputBytes`, which by design applies to what a single read leaves buffered. | kernel only |
| `Spec/Real/Equiv.lean` | The verified parsers match the hand-written (patched) ones they replaced: identical outcomes on every string of length ≤ 6–7 over small alphabets and on boundary cases with all prefixes (chunk-size lines, trailers, header lines). Request lines: identical on every complete line (all 40 methods, odd targets/versions, limits); on truncated input the verified parser sometimes waits where the legacy one has already rejected an unknown method (`GETG`), never the reverse — 12 of 17,997 prefixes. | compiler (`native_decide`) |
| `Spec/Real/Original.lean` | The shipped parsers are not prefix-consistent (`5;` vs `5;a=b\r\n`; `X` vs `X:a\r\n\r\n`). | compiler (`native_decide`) |
| `Spec/Real/Fixed.lean` | The hand-written patched parsers pass a bounded prefix-consistency check. | compiler (`native_decide`) |

With the verified parsers in place, the patched copy still passes the FRO's 24 HTTP test files and
the new regression tests, and the network tests (every 2-way split of 150 inputs, byte-at-a-time
delivery, 3,000 random splits) match single-write delivery.
