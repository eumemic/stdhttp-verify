| `Spec/Message.lean` | Request messages as relations on bytes (RFC 9112 §2.1, §3, §5, §6, §7.1): `HeadBytes` (empty lines, request line, field lines, `CRLF`), `ChunkedBody` (chunks, last chunk, trailer section), `BodyOf` (a body delimited as `Framing.Assigns` says), `RequestBytes w h d` (one request with head `h` and decoded body `d`), `Requests w n` (`n` requests in a row). Where RFC 9112 lets a recipient choose, the grammar takes the strict option: lines end in `CRLF` only, field values have no `obs-fold`, and Content-Length is one field line with one value. Two choices follow `Std.Http`, documented where they are made: chunk-size lines use the grammar of `Spec/Chunked.lean`, and the request-target is any non-empty run of `VCHAR`. | kernel only |
| `Spec/MessageExamples.lean` | Two requests that satisfy `RequestBytes`: `GET / HTTP/1.1` with `Host: a` and no body, and `POST / HTTP/1.1` with `Transfer-Encoding: chunked` and a body that decodes to `abc`. | kernel only |
| `Spec/Real/Machine.lean` | `reads_requests`: start from a fresh `Machine .receiving` (as the server does) and apply any sequence of the operations the server performs (`Server/Connection.lean`): feeding bytes split in any way, stepping, pulling body chunks, sending a response and its data, answering `Expect: 100-continue`, closing with an error, ending the input. The bytes the reader has consumed are `reader.messageCount` complete request messages followed by the part of the next one that its state describes, and the head it recorded is that message's: the method its token names, the request-target the URI parser makes of its target bytes, its header fields in order, and its version. `nothing_after_rejection`: once the reader has failed (rejected its input) or closed, it stays failed or closed under every further operation and accepts no more bytes. | kernel only |
| `Spec/Unique.lean` | The message grammar splits a byte stream in only one way. `request_unique`: a request message at the start of a stream is determined by the stream (its bytes, head and decoded body). `requests_unique`: two splittings of a stream into request messages agree (one list of messages is a prefix of the other). `chunked_partial_prefix`: the start of a chunked body decodes to the start of what the whole body decodes to. | kernel only |
| `Spec/Real/NoDesync.lean` | `no_desync`: take the bytes the machine has accepted under any sequence of operations, and any split of them into request messages `ms` followed by other bytes (how a front end that uses the same grammar divides the stream). Unless the reader has failed or closed: the requests it has finished and `ms` agree (one list is a prefix of the other); while it reads a request's body, the head it recorded (method, request-target, header fields, version) is that of the next message of `ms`; when it has finished a request, the bytes it consumed for it are that message. `pulled_bodies`: for every request of `ms`, the data of the body chunks `pullBody` handed out for it, in order, is the start of its decoded body (so each chunk is the next piece of the body), and all of it if one of those chunks was marked final. A handler that responds before reading the whole body gets no more of it (the machine drains the rest). | kernel only |

| `Spec/Real/Segment.lean` | `si_processRead`, `si_pullBody`: the read loop and the pull loop depend only on the machine's unread bytes, not on where they sit in the buffer. `ce_processRead`, `ce_pullNextChunk`: nothing they compute depends on the event queue. | kernel only |
| `Spec/Real/Events.lean` | `ev_processRead`, `ev_pullNextChunk`: the read and pull loops only append events, and what they append does not depend on the events already queued. | kernel only |
| `Spec/Real/Absorb.lean` | `read_split`: before the end of input is signalled and before a response is sent, within the buffer limit, feeding `x` and running the read loop, then feeding `y` and running it again, ends in the same machine as feeding `x ++ y` and running it once. "The same" means: up to where the unread bytes sit, with the same events apart from requests for more input (the split run has extra `needMoreData` events), after finishing a rejection's failure handling, and, once the reader has rejected the input or closed, up to the buffer and the body-byte count, which it no longer reads. `pull_split`: likewise for body pulls. If feeding `x` and pulling hands out nothing, then feeding `y` and pulling hands out the same as feeding `x ++ y` and pulling once, and the machines agree as above; this assumes the chunk being read fits the body limit, which holds in every machine the server reaches (`Budget.lean`). | `Spec/Real/Budget.lean` | `chunkBudget_run`: in every machine reachable from a fresh machine under the server's operations, the chunk being read (or about to be read after `100 Continue`) fits `maxBodySize`. | `Spec/Real/Drain.lean` | After a response has been sent, the reader reads the rest of the request body itself and discards it. `read_split_drain`, `pull_split_drain`: `read_split` and `pull_split` for a machine doing this, with one more possible outcome, `Lag`: the split run has consumed and counted `d > 0` more bytes of the current body data than the single run. This happens when all of a chunk's data has arrived but not its CRLF: the single run leaves the data buffered, the split run has already consumed the part that came in the first read. `lag_read`, `lag_pull`: on `Lag` machines the read loop and the pull loop end in the same machine as soon as the one behind reads on, or both wait and stay `Lag`; the events are the same apart from requests for more input, and neither hands out anything. `lag_feed`: feeding both the same bytes keeps them `Lag` (within the buffer limit of the one behind, which holds `d` more bytes). Not proven: that the write loop treats `Lag` machines alike (it reads only the reader's state and message count, which they share; checked by reading the code). | kernel only |

| `Spec/Real/HeadComplete.lean` | `head_read`: at the start of a request, with a request line and header lines within the limits unread (HTTP/1.1 or 1.0, a method `Std.Http` recognizes, a target the URI parser accepts — `URIComplete` gives every target in the RFC forms within the limits — ASCII field values), the read loop records the head, each header line in order with its lowercase name and its field value, and hands it to `processHeaders`. | kernel only |
| `Spec/Real/BodyComplete.lean` | `request_read`: the machine reads every request within its limits. With a whole request unread at the start of a request (nothing sent yet), the read loop records the head and pulls deliver the body's data, complete the body, and leave the following bytes unread. The conditions beyond `head_read`: the target's form suits the method (`TargetSuits`, RFC 9112 §3.2); in HTTP/1.1, or when a Host line is present, exactly one Host line whose value `Std.Http`'s Host check accepts (`HostAccepted`; `URIComplete` proves it for every Host value within the limits); no Expect line in HTTP/1.1 (`request_read_continue` drops this condition: with `Expect: 100-continue` the reader waits, a pull hands out nothing, and after the application answers `canContinue .continue` the pulls deliver the body); RFC 9112 §6.3 assigns the body length (`Assigns`) and the request meets `Std.Http`'s stricter framing rules (`StdFraming`: Transfer-Encoding on one line, without Content-Length, as bare codings with no parameters or empty elements, `chunked` last and only there); the body is within `maxBodySize`, `maxChunkSize`, `maxChunkLineLength` and the trailer limits (`BodyFits`). | `Spec/Real/SplitComplete.lean` | `split_read`: the same requests, however they arrive. Start at a request boundary (nothing sent, the input not ended while bytes remain) and apply any sequence of the connection loop's reading operations: feeds that split the request (and what follows it) into reads in any way, steps, body pulls, the application's `canContinue .continue`, and the end of the input after the last byte, in any order, with no read overflowing the buffer (`NoOverflow`; a read that would overflow is rejected, `feed_overflow`). Then a step, `canContinue .continue` (for a request with `Expect: 100-continue` the application has not answered) and enough pulls complete the body: over the whole run the pulls hand out chunks not marked final, then one marked final, and their data together is the body's data; the reader is done with the request (complete, or closed if the connection is not kept alive or the input has ended) and has recorded the head. Conditions: those of `request_read` other than the one on Expect (`ReqOk`). `split_read_bound`: `NoOverflow` holds when the request and what follows it fit `maxBufferedInputBytes`. The proof uses an invariant on where the machine is in the request (`Phase`): on any part of the head the read loop reads the complete lines and waits (`read_head`); on any part of the body a pull waits, hands out the next part of the data, or completes the body (`next_body`); and a step or pull only consumes input. | kernel only |
| `Spec/Real/DrainComplete.lean` | What happens to the reader once the application responds. `pull_twin`: the pull loop of a machine that has sent a response runs the pull loop of the same machine without the response, and goes on where that one hands out a chunk, so it reads and discards the body (`drain_pull`). `wr_processWrite`: the write loop leaves the reader unchanged, kills it, or resets it for the next request after a completed response; the application's writer operations (`send`, `sendData`, `userClosedBody`, `setKnownSize`) leave it unchanged or kill it (`wo_*`). | kernel only |
| `Spec/Real/ConnComplete.lean` | `conn_read`: every request on a connection is read. Start at a request boundary, with the unread bytes and the bytes the operations feed making up requests `Rs`, each meeting `ReqOk`, then anything. Apply any sequence of the connection loop's operations (`ConnOps`): reads split in any way, steps, pulls, the application's `canContinue`, its response head, data, end of body and size, and the end of the input after the last byte, with no read overflowing the buffer (`NoOverflow`) and no action of the application killing the reader (`NoKill`: a malformed response, or rejecting `Expect: 100-continue`, ends the request by design). Then every request before the current one is done, its pulled chunks delivering all of its data with the last marked final, or, if the application responded before reading the body, a prefix of it (the rest was read and discarded); the current request is in a phase of being read; the machine rejects none of them. `conn_finish`: once all of a request's bytes have arrived, a step, `canContinue .continue` and enough pulls finish it; after the application completes its response, the machine goes on to the next request while the connection is kept alive. | kernel only |
| `Spec/Real/URIComplete.lean` | `targetHost_ok`: `Std.Http`'s URI parser accepts every request-target in the four forms of RFC 9112 §3.2 — origin-form (`parseTarget_origin`), `http`/`https` absolute-form (`parseTarget_absolute`), authority-form (`parseTarget_authority`), `*` (`parseTarget_asterisk`) — and its Host check accepts every Host value `uri-host [ ":" port ]` for them (`hostParse_ok`; for CONNECT, the target itself, or its host alone when the port is 80 or 443); `reqOk_host` turns this into the `host` condition of `ReqOk`.
